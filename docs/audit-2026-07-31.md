# Importer audit — 2026-07-31

Full read of `includes/` across four angles: StepRegistry parity, idempotency and
shortfall reporting, scale, and security/seams. Every finding below was verified
against the code before being written down; the ones that were fixed were also
checked against a real fixture migration.

Fixed in `05078d5` and `7568495`. Everything under "Open" is real and unfixed.

---

## Verified clean — do not re-audit these

- **Security.** All 7 REST routes gate on `manage_options`; no `__return_true`
  anywhere. `/cleanup` additionally requires `confirm: true` and refuses while a
  job runs. There are no `wp_ajax` / `admin_post` handlers and no `$_POST` /
  `$_GET` / `$_REQUEST` reads in the whole plugin, so REST is the only mutation
  path. Every `$wpdb` value is bound; interpolated identifiers are all
  const-derived. The admin template is 100% `esc_html_*`; the JS is 100%
  `textContent` with zero `innerHTML`. The only destructive CLI command uses
  `WP_CLI::confirm( …, $assoc_args )`.
- **Seams.** Zero `$wpdb` in all 12 writers — every write goes through a
  BuddyNext service. Zero write verbs in `includes/Source/`. No writer imports an
  adapter. No `mvs_*` or `jt_*` table appears anywhere in `includes/`; partners
  are reached through their public APIs.
- **Pagination.** No `OFFSET` and no `SELECT *` anywhere. `activity_media_for()`
  is genuinely batched and `abstract`, so a per-row default cannot leak back in.
- **Background runner** cannot spin forever: every keyset reader orders ASC and
  takes the max returned id, so a full page always strictly advances the cursor.

## Fixed

| # | Defect | Where |
|---|---|---|
| 1 | Failed inserts mapped as successes. BuddyNext services return `(int) $wpdb->insert_id` — **0 on a failed INSERT, not a `WP_Error`** — and four writers tested only `is_wp_error()`. The row was mapped to nothing, counted, and skipped forever after. | `ActivityWriter` (post + comment), `SpaceWriter`, `ProfileWriter` (group + field) |
| 2 | **Privacy leak.** `ActivityWriter` resolves a group's posts through the `space` domain and guarded with `null === $mapped`, so a poisoned `0` fell through to `space_id = 0` — the global feed. One failed space insert republished a private group's whole history publicly, with every row count still reconciling. | `ActivityWriter::import_post()` |
| 3 | **Reactions truncated silently.** `favorites_count()` excludes `''` and `'a:0:{}'`; the fetch did not, and its `LIMIT` counts users while the loop emits favourites. One page of members who had un-favourited everything returned zero rows — and the reactions step is `empty_done`, so an empty batch reads as "domain finished". | `BuddyPressAdapter::reactions()` |
| 4 | `import_member()` returned a hardcoded `true`, discarding all four `SpaceMemberService` results, so a roster the target refused still reconciled as complete. | `SpaceWriter` |
| 5 | Five `ImportLedger::add()` calls cast `run_loop()` / `image_loop()` **arrays** to int, which is always `1`. A CLI migration of 4,000 avatars reported "imported: 1" against "expected: 4000". | `MigrateCommand` |
| 6 | `dm_thread` held a different quantity per surface — messages via the registry, conversations via the CLI — against a `message_threads` stat. Both now report threads accounted for, merges included. | `StepRegistry`, `MigrateCommand` |
| 7 | The background runner advanced its cursor past rows no batch accounted for. It now settles at the **end** of a domain the way the CLI always has. Clearing per batch would restart a domain holding one permanently-failing row on every tick and never finish. | `StepRegistry` (`gap`), `BackgroundImport` |
| 8 | Four source-count predicates disagreed with their fetches (comments/spam, follows/type, forum statuses), and four domains declared no stat at all. | `BuddyPressAdapter`, `BuddyBossAdapter`, `StepRegistry` |

Fixture evidence: source comment count went 26 → 24 and importable 21 → 19,
removing exactly the two seeded spam comments that had been reported as content
the migration failed to bring. Every other domain reconciled identically before
and after, and the privacy assertion passed in both runs.

**Note on the reserved-slug fixture.** It refuses a space via a `WP_Error`, which
`is_wp_error()` already caught — so that scenario does *not* exercise fix #1 or
#2. Those cover a failed INSERT returning `0`, which no current fixture
reproduces. Worth a fixture that forces one.

## Open — real, verified, not fixed

### Reporting

- **The activity domain reason-codes nothing.** `import_post()` has five distinct
  `return array( 'id' => 0, 'created' => false )` exits — no content/media, group
  never became a space, `hide_sitewide` with no space, blog post no longer
  public, write failed — all indistinguishable. No `skipped` key exists in the
  returned shape, and `migrate_activity()` never calls `report_skips()`. This is
  "N imported alone" in the largest domain. It is also why the activity
  checkpoint clears on most runs: deterministic skips are not counted as
  accounted, so the gap check fires legitimately every time.
- **`ForumImporter` drops every forum silently when `ensure_category()` returns
  0**, advancing `$last` past them first, with no reason code.
- **`import_blog_comments()`'s result is discarded**, and it only runs on the
  branch that *creates* the card — so a run that dies mid-thread never imports
  the remainder.
- Unmapped profile group drops its fields with no counter; activity media loss
  (missing file) is invisible and `activity_media` is compared against nothing.
- `ConnectionWriter` counts an already-existing connection as new and maps a
  *user* id as the mapping's `bn_id`.

### Scale

- **`images_for()` is not keyset-paginated** — it lists every owner id and skips
  linearly, O(n²/limit), and its `static` cache is per-request so each background
  tick re-runs two full `scandir()`s.
- **N+1s:** `message_threads()` runs 2 queries per thread; `forum_replies()` runs
  one `postmeta` query per reply (200k on a large bbPress); `ProfileImporter`
  runs 2 queries per user.
- **Unbounded reads inside one tick:** `thread_messages()` has no `LIMIT`;
  `get_comments()` in the blog mirror has no `number`; `SpaceImporter`'s inner
  member loop runs a whole group's roster with no deadline check and no inner
  checkpoint.
- `BATCH = 100` is a private constant with no filter, while a batch can be 100
  image re-encodes. `stats()` is expensive and is called on the polled `/summary`
  path with no caching. `VerifyService` samples with `ORDER BY RAND()`.

### Structural

- **The CLI does not use `StepRegistry`** — `migrate-all` is a hand-maintained
  ordered call list with its own `target_available()` guards. The order happens
  to match today (verified step by step), but nothing enforces it: an 18th
  registry entry runs everywhere except the CLI. This is card `10144240380`.
- **A stalled background job is never detected.** `status()` returns `scheduled`
  and `tick()` writes `updated_at`; nothing reads either. A tick that fatals
  leaves `state: running` forever and the UI shows a frozen progress bar. The
  data for a watchdog is already being written and thrown away.
- `ProgressController` defaults `phase` to the string literal `'profiles'`,
  restating registry step #1 outside the registry.
- The browser loop persists no checkpoint (`var after = 0`), so it diverges from
  the other two runners. Not a loss — it always re-scans — but it means a browser
  run ignores a cursor a background run left.

### Packaging

- There is no `.distignore` and no build script, so a naive zip ships `docker/`
  inside the plugin. Two files there matter: `reset-target.php` has no `ABSPATH`
  guard and truncates 18 tables, and `dev-auto-login.php` signs in as user 1 from
  a query string. Neither is remotely exploitable as shipped (the first fatals
  without `wp-load`; the second is inert outside `mu-plugins/`), but both belong
  outside the distributed artifact.
